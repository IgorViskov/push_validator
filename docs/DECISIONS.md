# Принятые решения

Четыре решения, которые определили форму продукта. Каждое с разбором альтернатив и с ценой,
которую за него платим.

---

## 1. Где хранить реестр репозиториев: отдельная реляционная БД

**Решение: добавить SQLite (EF Core), а не хранить реестр в уже поднятом Neo4j.**

Агент обязан быть персистентным: после `docker compose down` и повторного подъёма список
обслуживаемых репозиториев, установленные хуки и история прогонов должны остаться. Графовая
база в стенде уже есть, и соблазн сложить туда же узлы `:WatchedRepository` понятен —
одна база вместо двух.

### Хранить в существующем Neo4j

**Плюсы**

- одна база в стенде: один контейнер, один пароль, один том, одна резервная копия;
- нет второй технологии доступа к данным — только драйвер Bolt и Cypher;
- связи «репозиторий → его символы» выражаются рёбрами естественно, без склейки по ключу;
- нет расхождения между двумя хранилищами: транзакция одна.

**Минусы**

- **админка умирает вместе с графом.** Это решающий довод. Neo4j — самая тяжёлая и самая
  ломкая часть стенда: не хватило памяти под heap, не поднялся вовремя, повреждён том. Если
  реестр лежит там же, то в момент проблемы с графом пользователь теряет не только контекст
  влияния (это штатная деградация — анализ по диффу остаётся полноценным), но и возможность
  вообще что-либо сделать: увидеть список репозиториев, отключить сбойный, посмотреть, что
  было в прошлых прогонах. Инструмент управления обязан работать, когда управляемое сломано;
- данные табличные, а запросы к ним — табличные: «последние 20 прогонов репозитория X»,
  «сколько пушей остановлено за неделю», «средняя длительность». В Cypher это пишется, но
  выходит длиннее и без пользы от графа: у записи журнала нет связей, ради которых его
  выбирают;
- журнал прогонов растёт линейно и вечно. В графе кода он становится мусором, который
  участвует в обходах и полнотекстовом индексе, а при `--reset` репозитория его нужно
  аккуратно не удалить;
- нет миграций схемы. У графа схема необязательна, и это удобно для кода, но реестр —
  прикладная модель, которая будет меняться; отсутствие миграций означает ручные скрипты
  обновления;
- Community Edition отдаёт единственную пользовательскую базу, то есть изолировать реестр
  от графа даже логически нечем.

### Добавить реляционную БД

**Плюсы**

- **изоляция отказов**: админка, реестр и журнал живут, когда граф недоступен. Граф в этой
  системе — производные данные: он целиком восстанавливается переиндексацией из исходников,
  а реестр — нет;
- запросы журнала пишутся так, как думают о них: `ORDER BY`, `GROUP BY`, индекс по
  `(RepositoryId, StartedAt)`;
- миграции EF Core дают схеме понятный путь развития;
- разделение по смыслу: граф отвечает на вопросы о коде, реляционная база — о работе агента.
  Это разные жизненные циклы и разные частоты изменения.

**Минусы**

- два хранилища: две резервные копии, два места, где может кончиться место на диске;
- нет транзакции поперёк границы. Реально это проявляется так: репозиторий удалён из реестра,
  а его узлы в графе остались. Лечится тем, что удаление чистит граф явно, а несогласованность
  безвредна — осиротевшие узлы никем не запрашиваются, потому что запрос всегда идёт по ключу
  репозитория из реестра;
- вторая технология доступа к данным в коде (EF Core рядом с драйвером Bolt).

### Почему SQLite, а не PostgreSQL

- **не добавляет контейнера.** Требование «запускаем докер образ, в нём уже есть все нужные
  части» и без того нарушено графовой базой; добавлять третий контейнер ради таблицы
  из четырёх колонок — плохая сделка. SQLite — файл на томе: ни порта, ни пароля, ни ожидания
  готовности при старте;
- нагрузка этого не требует. Пишущий один — сам агент, и пишет он один раз на прогон,
  то есть раз в минуты. Читает админка, тоже один человек;
- переезд дешёвый: реестр за интерфейсом `AgentDbContext`, смена провайдера EF Core —
  одна строка в регистрации плюс перегенерация миграций. Момент для переезда наступит, когда
  агентов станет несколько на один реестр: у SQLite один писатель, и здесь он упрётся.

**Цена решения**: два хранилища вместо одного и отсутствие сквозной транзакции. Принято,
потому что доступность управления важнее единственности хранилища, а согласованность здесь
и не нужна — граф производный.

## 2. Графовая база — отдельным контейнером, а не встроенным движком

**Решение: оставить Neo4j в отдельном контейнере, агента поставлять образом, работающим
и без него.**

Формулировка «в нём уже есть все необходимые части» тянет к одному контейнеру. Альтернатива
у неё одна: положить граф в тот же SQLite (таблицы узлов и рёбер, обход рекурсивными CTE).

**Почему не так**

- обход графа с ранжированием — не «SELECT с JOIN». В текущей реализации это два канала
  поиска точек входа (структурный и полнотекстовый Lucene), слияние Reciprocal Rank Fusion,
  обход по 13 типам рёбер с весами и затуханием, поправка на намерение запроса, отбор с
  ограничением на файл. Переписать это на рекурсивных CTE — не перенос, а вторая реализация
  поискового движка;
- полнотекстовый индекс по именам, сигнатурам и XML-комментариям в SQLite есть (FTS5), но
  без Lucene-синтаксиса с бустингом термов, на котором держится структурный канал;
- граф — это состояние, которое должно переживать пересборку образа. Внутри контейнера ему
  всё равно нужен том, то есть выигрыш «одна часть вместо двух» получается только на бумаге.

**Что сделано, чтобы это не било по пользователю**

- недоступный граф — штатная деградация, а не отказ: состояние `impact` добавляет
  `Info`-находку «граф не ответил» и уходит в анализ по одному диффу. Проверка остаётся
  полноценной, просто без контекста влияния;
- `docker compose up -d` поднимает обе части одной командой и ждёт готовности графа
  по healthcheck;
- реестр и админка от графа не зависят вовсе (см. решение 1).

**Цена**: два контейнера вместо одного, около 600 МБ образа Neo4j, порядка 40 секунд
на первый подъём.

## 3. Образ агента на базе SDK, а не runtime

**Решение: `mcr.microsoft.com/dotnet/sdk:10.0` в рантайме.**

Требование «агент сам поддерживает графовую БД в актуальном состоянии» означает, что разбор
C# происходит в контейнере на каждом пуше. Разбор идёт по семантической модели Roslyn —
только так вызов `_prices.CalculateTotal(order)` превращается в ребро к конкретному методу
конкретного типа, а не в текстовое совпадение имени.

`MSBuildWorkspace` открывает решение силами настоящего MSBuild и требует установленный SDK.
Без него происходит худшее из возможного: решение открывается, ошибки нет, но ссылки
не разрешаются — семантическая модель молча перестаёт находить символы, и половина рёбер
`CALLS` не появляется. Граф выглядит наполненным и отвечает неправдой.

**Альтернативы**

- `aspnet:10.0` + разбор по синтаксису без семантики: дешевле на 600 МБ, но граф вызовов
  вырождается в поиск по именам, а вместе с ним теряется главная функция продукта;
- индексация вынесена во второй образ с SDK: контейнеров становится три, а выигрыша нет —
  SDK всё равно скачивается.

**Что сделано**: при старте агент печатает найденный SDK, а страница «Настройки» показывает
его состояние явно — чтобы «SDK не найден» выяснялось при запуске, а не на демонстрации.

**Цена**: образ около 800 МБ против 220.

## 4. Настройки — только из конфигурации образа, без правки из админки

**Решение: страница «Настройки» показывает применившиеся значения и имя переменной окружения
для каждого; редактирования нет.**

Требование — «для всех настроек должна быть возможность настроить их для докер образа».
Соблазн — добавить сверху редактирование в UI, «чтобы удобнее».

**Почему нет**: два источника правды у одной настройки означают, что после перезапуска
контейнера агент ведёт себя не так, как вчера, а причина не находится ни в compose-файле
(там записано одно), ни в UI (там показано другое). Для инструмента, который блокирует
пуши, «вчера пропускал, сегодня блокирует, и никто не менял настройки» — худший вид отказа.

Исключение сделано для того, что относится к конкретному репозиторию, а не к агенту: путь,
файл решения, участие в обслуживании. Это данные реестра, у них источник правды один — база.

**Цена**: чтобы поменять порог сложности, нужно править `.env` и перезапускать контейнер.
